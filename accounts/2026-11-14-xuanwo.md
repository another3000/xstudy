## 1. 一句话定性

## 2. 人设与定位

- **Bio 承诺：** 数据自由、OpenDAL、LanceDB 上的 RBIR。身份是开源基础设施，不是博主。
- **时间线实际：** 近窗主线非常集中——本地 Mac 跑不稳他的 LOOP 之后，把环境迁到远端服务器。长文《From Codex App to T3 Code》写清：Codex App 在远程不能真正创建 thread（管理能力是 App 侧 MCP，远程只能查和读），为了绕过他被迫维护一个 thread 技能；Lody 设计对但数据要放别人服务器，公司不允许；T3 Code 思路相近，却可以自建服务器和 Relay。跟进帖把 T3 Code 的任务收件箱拆成 Inbox / Working / Snoozed / Settled。旁支是向 Magpie 提远程 API 和 Antigravity 兼容、引用「叶天帝」演示、吐槽 Gemini 周边生态。
- **目标受众：** 正在把 Agent 工作流从笔记本迁到服务器的华语工程师，以及 OpenDAL 用户。
- **差异点 / 人设钩子：** **先写清「为什么旧方案在远程死掉」，再给可自托管的替代。** 限制条件（数据不能出公司、远程不能建 thread）本身就是专业性。
- **与 Bio 的错位：** Bio 是数据底座，近窗大半是 Agent 工作流。OpenDAL 只在一条感谢用例投稿的帖里出现。人设没崩，但读者先看到的是 ADE 迁徙，不是对象存储。

## 7. 可学习清单（→ 微李玩AI / LIS / AI入企 / 小程序）

1. **先写旧方案在现场哪一步死掉** → AI入企：不要只说「我们换了工具」。写成「远程环境只能查线程、不能创建，所以编排断了」。
2. **把公司约束写进选型** → LIS / 输血信息化：「数据不能放到第三方服务器，即便有端到端加密」。这比「更安全」可核对。
3. **给任务一个四态收件箱** → 微李玩AI / 院内 AI 工单：Inbox / Working / Snoozed / Settled（外加 Archive）。每天的目标是清零 Inbox，而不是「再跟一跟」。
4. **备选方案也要写淘汰理由** → 对照他不用 Lody、不继续死磕 Codex App。内部选型纪要至少保留一条「为什么不选 B」。
5. **长文负责说透，短帖负责拆出一个可抄结构** → 迁移长文之后立刻补 Inbox 四态，让没时间读全文的人也能带走一块。

## 8. 风险与不该学

- 「太垃圾了」「灭杀一切敌」在工程师圈子里是气氛，放进医疗品牌会先损耗信任。
- 高频向作者公开提需求有效，但不要变成催更表演。
- 粉关比低于许多华语增长号，不必模仿他的关注半径。
- Bio 与近窗主题不完全重合：如果要迁「人设」，先在简介里补一句正在做的工作流，免得新读者迷路。
