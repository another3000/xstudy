5. 增长机制拆解

  1. 互关 / 粉关比：约 20.5:1，健康。
  2. 回复工时：这是近窗的主产能。主帖少，不等于号静默。
  3. 钩子话术：夸张结果（iPad 装 macOS）；否定句安抚（「不是你的账号被封了」）；发车带「现在能做什么」。
  4. 平台激励：蓝标；未见分成话术。
  5. 擦边 / 猎奇：无。夸张演示是能力秀，不是擦边。
  6. 跨平台导流：站点 diygod.cc，产品在帖里用截图和说明自证，不靠长链口号。
  7. 其他：公开建造 + 把验证边界写清楚（「审批截图会画出路线；目前只在模拟器上测过」）。这比「全平台已支持」更可信。

7. 可学习清单（3–5）

  1. 发车写成「谁提出 → 今天加上 → 现在能做什么」→ 微李玩AI / 小程序：版本说明不要只写「优化体验」，写清来源和验证范围。
  2. 夸张演示只当钩子 → AI 入企可以用一个醒目的现场（「在手机上跑完，不需要电脑」），后面必须接真实边界。
  3. 把验证写到哪一步 → 「我本地验证过，对端还没试，谁跑通了请回一声」——适合院内联调，也比假装全部跑通更安全。
  4. 故障沟通用否定句先安抚 → 客户群或内容号：「不是你的账号出问题，是服务故障」。学结构，再由人审后发出。
  5. 回复可以多，但资产在主帖 → 不要把串门当成已经「做了内容」。

8. 风险与不该学

  • 限流 / 审核风险：低。夸张演示若被理解成承诺，会有信任风险。
  • 信任与品牌损耗：Bio 的角色扮演对新读者不友好；公开骂/催上游工具可以，持续刷同一 bug 会吵。
  • 与我们定位冲突点：院内交付不能用「给 iPad 装上 macOS」这种秀；要迁移的是发车格式和验证边界。

9. 对我们的行动建议

  1. 本周选一个真实改动，写成 4 行：谁提的、今天改了什么、现在能做什么、我验证到哪一步（人审后发）。
  2. 准备一条故障沟通草稿：「不是你的账号/环境独有问题，是××在××时间出现了××」，先安抚再给处理进度。
  3. 连续几天的回复可以保留，但至少保证 2–3 条主帖是产品现场，而不是全部泡在评论里。
